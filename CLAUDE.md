# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

**Totempoint** — self-service ordering totems for food businesses, plus the multi-tenant back office behind them. A customer orders from a tablet at the counter and the ticket reaches the business; one installation serves many brands, each with its own catalog, cover screen and staff. It was scaffolded with [Lovable](https://lovable.dev) (see `.lovable/`) as a single-brand burger demo called "Burger Point"; that demo was deleted and the name is gone — don't reintroduce it anywhere, in copy, titles or metadata.

`README.md` describes the product and how to run it.

`PARA-NICOLAS.md` is a handoff briefing in Spanish: the business rules and invariants that must not be changed, and the work still pending. Keep it in sync when either of those moves.

## Team agents

Shared subagents live in `.claude/agents/` (committed, so everyone on the repo gets them). Use them proactively:
- **code-reviewer** — after writing or changing non-trivial code, review the diff (security, multi-tenant isolation, bugs).
- **arquitecto-ts** — before building a new feature or changing structure, to design it against the project's patterns and invariants.
- **test-engineer-ts** — for tests of permission rules and pure business logic (`bun test`), following the deliberately narrow coverage.
- **doc-writer** — for README/guides/module docs.

The `.NET`-flavoured agents some devs have user-globally (dotnet-*) do **not** apply here: this is TypeScript/TanStack/Drizzle, not C#.

## Commands

Package manager is **bun** (`bun.lock`, `bunfig.toml`), not npm/pnpm.

```sh
bun install         # install deps
bun run dev          # vite dev server, fixed port 8081 (strictPort)
bun run build        # production build (nitro)
bun run build:dev    # build in development mode
bun run preview      # preview a production build
bun run lint         # eslint .
bun run format       # prettier --write .
```

Tests run with bun's built-in runner (`bun run test`). Coverage is deliberately narrow: `src/lib/auth/permissions.test.ts` pins the permission rules, which are the part that fails silently. Everything else is still verified by hand.

**Two databases on the same Railway MySQL server: `totempoint_test` for development and `railway` for production.** `.env.local` points at `totempoint_test`, so `bun run dev`, every script and every manual test write there; the deployed app on Railway reads `railway` through its own env var. Production is touched only on purpose, with `bun --env-file=.env.produccion.local run src/db/<script>.ts` (that file holds the production URL and is git-ignored like every `*.local`); `src/db/index.ts` prints a warning when a script runs against it. A migration therefore runs twice: on test first, then on production. Until 2026-10-06 there was only one database and local tests wrote real data — never point `.env.local` back at `railway`. `totempoint_test` started as a full copy of production on that date.

**The shared MySQL server has a 151-connection limit, and on 2026-10-06 it filled up**: the dev server created a new pool on every hot reload without closing the old one, and every deploy left the previous container's connections open until MySQL's 8-hour `wait_timeout`. `src/db/index.ts` now keeps one pool across reloads in development and closes idle connections after 60s (`maxIdle: 2`, `idleTimeout`), and the server's `wait_timeout`/`interactive_timeout` were set to 900s with `SET GLOBAL`. That setting is lost if Railway restarts MySQL: if "Too many connections" shows up again, check `information_schema.processlist` and set it again.

Database (Drizzle + MySQL on Railway): there are no `db:*` npm scripts, so drive `drizzle-kit` directly, e.g. `bunx drizzle-kit push` or `bunx drizzle-kit generate`. `drizzle.config.ts` reads `DATABASE_URL` from `.env.local` (not `.env`), i.e. the test database. Seed a superadmin user with `bun run src/db/seed.ts` (reads optional `SEED_EMAIL`/`SEED_PASSWORD` env vars, defaults exist). New companies get the base movement reasons automatically (`cargarMotivosBase` in `src/lib/stock/motivos-base.ts`, called by `createBusiness`); without them the Stock section shows its button but the "Motivo" dropdown is empty and not even the opening stock can be registered. `bun run src/db/seed-action-codes.ts [slug]` fills in the ones missing on companies created before that.

`bunfig.toml` enforces a 24h supply-chain guard on new package versions (`minimumReleaseAge`). Don't add entries to `minimumReleaseAgeExcludes` without confirming with the user first.

`.gitattributes` pins the repo to LF (Prettier's default). Before it existed, Windows checkouts rewrote files to CRLF and `bun run lint` reported ~15k phantom `Delete ␍` errors. About 321 real formatting errors remain in files nobody touched (`components/ui/*`, older admin sections); `bun run format` fixes them but rewrites half the repo, so coordinate that with the team rather than doing it inside an unrelated change.

## Architecture

### One totem flow: `/t/$empresa/$local/$totem`

- **`/t/$empresa/$local/$totem/*` is the totem**, multi-tenant and the only ordering flow there is. The URL names the company slug, the branch slug and the totem's number, so a location with several tablets gives each one its own address. Routes: `t.$empresa.$local.$totem.index` (cover), `.categorias`, `.menu.$category`, `.combos`, `.carrito`, `.checkout`, `.pagar.$orderId`, `.listo.$orderId`. It reads the DB catalog through `src/lib/api/totem.functions.ts` and persists real orders.
- The old single-brand Burger Point demo (`src/lib/menu.ts`, `src/lib/store.ts`, `TotemHeader`, and the bare `categories` / `menu.$category` / `cart` / `checkout` / `confirmation.$orderId` routes) **was deleted**: it served a hardcoded menu whose orders never reached the database, and a tablet left on `/` could take fake orders. Don't reintroduce a demo flow at the root.
- **`/` is the platform's landing page**, not a business: the Totempoint pitch plus a link to `/login`. A totem is always opened by its own slug URL.

### The public totem layer (`src/lib/api/totem.functions.ts`)

This is the **only file with server functions that have no auth middleware** — the totem runs without a session. Everything else in `src/lib/api/` requires `requireAuth`/`requireSuperadmin`, so keep authenticated helpers out of this file to avoid accidentally exposing them.

- `resolverTotem` resolves the URL to a company and a location: `companies.slug` → `locations.slug` (unique per company) → the `totems` row with that `number`. All three must exist and be active, or the totem shows an error instead of somebody else's menu. Both slugs are generated from the name and checked against `RESERVED_SLUGS` in `src/lib/slug.ts`, because the company slug is the first segment of a path that also holds `/admin`, `/login` and `/img`.
- `getTotemHome` (cover), `getTotemMenu` (catalog + combos), `createTotemOrder`, `getTotemOrder`.
- `createTotemOrder` receives lines of `{kind: "producto" | "combo", id, quantity}`; **prices and the total are recomputed server-side** from the DB. Never trust amounts sent by the client. A combo is stored as one `order_items` row with `product_id` null and the combo's name and price, which `order_items` already freezes.
- **Removing an ingredient ("sin cebolla") is per product and the owner decides.** `products.customizable` turns the option on for a product and `product_ingredients.removable` says which ingredients may go — both must be true, and both are off by default, so nothing becomes configurable on its own. The totem only ever offers what those two flags allow, and `createTotemOrder` revalidates it against the recipe rather than trusting the tablet. Removing never changes the price. What the customer took out is frozen per line in `order_item_removals` (name included, like `order_items` freezes the product name) and the kitchen prints it under the line. The cart keys a line by `kind + refId + what was removed`, so the same product with and without tomato are two lines and not quantity 2 — which is also why the order's product ids are deduplicated before checking availability.
- **Bread choice (pan blanco / negro)** is a product attribute, not a modifier: `products.pan` is `blanco` or `negro` when the sandwich is made in only one (the menu just says so), `ambos` when the customer picks, null when it doesn't apply. The picker (`ElegirPan`) sits inline in the product card on both the totem and the online menu, preselected on blanco, so the add button never moves. The cart keys a line by its bread too (`claveDe`), `createTotemOrder`/`createOnlineOrder` take `pan` per line but the server decides (fixed bread wins; `ambos` defaults to blanco for a stale cart), and `order_items.pan` freezes it so the kitchen, the ticket and the tracking page show it. Combos don't ask: their components go as the counter makes them. `bun run src/db/migrate-pan.ts` adds both columns.
- **"Cada 12, 2 de regalo"** is a category rule (`categories.regalo_cada` / `regalo_cantidad`, set in Categorías): every 12 **paid** units the customer gets 2 free, and **picks them**. Categories with the same rule pool their units and a combo counts by its components ("12 clásicos" is twelve), but units inside a combo can never be the free ones. With 14 loose sandwiches they pay 12 (the cheapest two are free); with 12, or a 12-combo, the cart says 2 are due and to add them. `calcularRegalo` in `src/lib/regalo.ts` is the DB-free arithmetic, covered by `regalo.test.ts`; the cart line carries its rule (`TotemCartItem.regalo`, refreshed by `reprice`) so `cartTotal` already subtracts the gift on every screen, and `tomarPedido` recomputes it from the database, subtracts it from the total and freezes `orders.regalo_descuento` (what was taken off) and `orders.regalo_unidades` (gifts due but not added, which the kitchen picks). Mercado Pago gets a single line for the paid amount when there's a gift, because it doesn't accept negative lines. Category taglines go up to 255 characters. `bun run src/db/migrate-regalo.ts` adds the columns.
- **Combos a elección** ("18 empanadas clásicas, los gustos que quieras"): `combos.grupos` (JSON: `nombre`, `cantidad`, `categoriaIds`), set in Combos → "A elección del cliente", on top of the fixed `combo_products` (Chiqui's "Planazo" = 8 chosen + 2 fixed beers). The menu sends each group with the options this branch sells today (not off, not sold out); a group with no options hides the combo. The online card opens an inline picker (`ElegirGustos`: a counter per flavour, "6 de 18", "Repartir el resto"); the cart keys the line by its choices, `createOnlineOrder` takes `elecciones` per line and `tomarPedido` revalidates them (exact sum per group, allowed category, available) and freezes them in `order_item_elecciones`, which the kitchen, ticket and tracking show. Chosen units deduct stock as loose products. They don't count toward the gift rule. The **totem has no picker yet**, so `getTotemMenu` filters those combos out. `bun run src/db/migrate-combos-a-eleccion.ts` creates it.
- Products with no `categoryId` are grouped under a synthetic category with id `0` (`UNCATEGORIZED`, shown as "Otros") so they can't become invisible.
- Order numbers restart at 1 every morning per location and are assigned by an atomic counter (`order_sequences`), not `MAX(order_number) + 1`: that read doesn't lock, so two orders arriving at the same location at once read the same max and the second collides against the `orders_location_date_number_uq` unique key — a lost order at scale. The counter is bumped with `INSERT ... ON DUPLICATE KEY UPDATE last_number = LAST_INSERT_ID(last_number + 1)` inside the order transaction, and its row lock serializes only the orders of that same location and jornada; different locations are different rows and never contend, so many businesses can take orders in parallel. `LAST_INSERT_ID()` reads back the assigned number in the same round trip, before the order insert overwrites it with its own autoincrement id. `bun run src/db/migrate-order-sequences.ts` creates the table and seeds it from existing orders. The totem knows its own location from the URL, so the order, its price overrides (`locationPrices`) and its availability all belong to that branch.
- Per-location availability (`locationProducts`/`locationCategories`/`locationCombos`) **is** applied, in `getTotemMenu` **and** in `createTotemOrder`: the cart lives in the tablet and outlives somebody turning a product off from the panel, so checking it only when drawing the menu let a stale cart through. Absence of a row still means available.
- A combo is unavailable at a branch for either of two reasons, and only the first is stored: the `locationCombos` switch in the Disponibilidad section, or — computed, never written — any of its component products being off at that branch or inactive company-wide. Storing the second would mean remembering to turn off every combo by hand each time a product goes off, and the day somebody forgets, the totem sells something the counter cannot hand over. `bun run src/db/migrate-location-combos.ts` creates the table.

### Modules: totem and online are sold separately

A company contracts the **totem**, **online ordering**, or both (`companies.totem_enabled`, `companies.online_ordering`), toggled per company by the superadmin (`setBusinessModule`, audited; at least one must stay on) and chosen when creating it. Everything that belongs to the company — catalog, prices, availability, stock, kitchen, cash, Mercado Pago, operators and **appearance** (accent, base, fonts, corners in `totem_settings`) — works for either; only what belongs to a channel depends on its module. Without the totem module the panel hides Tótems, the "Apariencia" section hides the totem cover (template, hero, texts, preview), `resolverTotem` refuses `/t/...` and `createTotem` refuses; without online the panel hides "Pedido online", `resolverOnline` refuses and `online.functions.ts` refuses. Turning a module off deletes nothing. The admin's `SectionDef.modulo` gates a section; the server is still the boundary. `bun run src/db/migrate-modulos.ts` adds both columns (totem on for existing companies, online on for those already using it).

### Online ordering: `/p/$empresa/$local`

A second sales channel of the same company, not a separate product: the customer opens `/p/{empresa}/{sucursal}` on their own phone, browses the same menu as the totem (`armarMenu`), and picks pickup (`deliveryMethod: "mostrador"`) or delivery (`"envio"`). Routes: `p.$empresa.$local.index` (menu, one scrolling list with sticky category chips), `.carrito` (cart + checkout on one screen) and `.pedido.$token` (tracking, polls itself). The cart reuses `totem-cart.ts` under the key `online:{empresa}/{local}`.

- The public server functions (`getOnlineMenu`, `createOnlineOrder`, `getOnlineOrder`) live in `totem.functions.ts` next to the totem's, and **both channels take orders through the same `tomarPedido`** — pricing, extras, removals, availability, numbering, stock and Mercado Pago are one code path. Don't fork it.
- **Delivery works like PedidosYa/Rappi, never by customer-picked zones** (that first version was rejected: a zone name is useless to the rider). The customer searches their address (`BuscadorDireccion`, Google Places Autocomplete) or uses GPS, confirms the exact point on a Google map with a draggable pin (`MapaPin`), and adds details (floor, "sombrilla roja"). The fee comes from the **driving distance** between the branch (`online_settings.origin_lat/lng`, set by the owner on a map) and that pin, priced by the owner's tiers (`delivery_tiers`: "hasta 2 km, $1.500"; the longest tier is the max reach). The phone shows a **straight-line (haversine) estimate** while the pin moves (`src/lib/delivery.ts`, pure and shared); `createOnlineOrder` recomputes the fee server-side with the **Google Routes API** (`computeRoutes`, `src/lib/maps/distance-server.ts` — the legacy Distance Matrix is not enabled on new projects), falling back to haversine if Google is down — so a sale is never lost, the same rule as Mercado Pago. Never trust the phone's amount. The minimum is measured without the fee; the order freezes address, details, point, distance and fee (`delivery_*`, fee already in `total`). Tier changes are audited as prices. Config lives in the owner-only "Pedido online" section (`OnlineSection`, `online.functions.ts`). `delivery_zone_name` and the `delivery_zones` table are leftovers of the zone version; `migrate-envio-por-distancia.ts --limpiar` drops the table once the zone code is no longer deployed.
- **Google Maps, not OpenStreetMap.** The earlier Photon/OSM/Leaflet stack was replaced because Google's address data is better (it has the house numbers OSM lacked in Cariló and countrys), so the old "street-alone + `aproximada`" fallback is gone. The browser SDK (Places + Maps + Geocoding, pinned to `v3.64`) loads once through `cargarGoogleMaps` (`src/lib/maps/google.ts`); the **browser API key** is served at runtime by the public `getPublicConfig` server fn (`src/lib/api/config.functions.ts`) from `GOOGLE_MAPS_KEY`, so it never lands in the bundle — restrict it by HTTP referrer in Google Cloud. Autocomplete returns only predictions; coordinates are fetched on pick (`detalleDePlace`, Place Details), grouped by an `AutocompleteSessionToken` so Google bills one session per address. Reverse (GPS / moving the pin) uses the browser `google.maps.Geocoder`. The Routes API is the one server-side call and needs a key that works off-referrer: `GOOGLE_MAPS_SERVER_KEY`, falling back to `GOOGLE_MAPS_KEY`. Enable Maps JavaScript, Places, Geocoding and Routes APIs. This reversed the project's old "no vendor that needs a credit card" rule (Google Maps Platform requires a billing account) — that rule still holds for storage (no S3/R2); maps is the deliberate exception.
- `delivery_approx` (`migrate-direccion-aproximada.ts`) still exists: when set, the kitchen's "Cómo llegar" navigates to the written address (`linkNavegacionADireccion`, a plain Maps URL, no API key) instead of the point. With Google it is rarely set, since the point is the door.
- An online order waits in the kitchen's "Por aceptar" band (beeps and vibrates while any is pending) until someone accepts it with an ETA (`acceptOnlineOrder` → `accepted_at`, `eta_minutes`); `setOrderStatus` refuses to move it before that. Rejecting is `cancelOrder`, so stock and refunds behave as for any cancellation.
- **A company with several branches has one link: `/p/$empresa`** (`p.$empresa.index.tsx`, `getOnlineEmpresa`). The customer picks Envío or Retiro; for delivery they search their address and see **every branch that reaches it** (the client's own haversine + each branch's tiers, the same data each menu already carries), with distance, fee and whether it's open, and **they choose** (Sebastián's call — not auto-assigned). A closed branch is listed, disabled, with when it opens, and the open ones go first: the order goes to one that can make it now. It is shown even with a single branch, because it is also the brand's cover: there Retiro and Menú go straight to that branch with no one-item list, and Envío still asks for the address to check the reach. The choice reaches the branch through the phone, never the URL (an address is personal data): `src/lib/online-eleccion.ts` stores `{entrega, destino}` for that cart key, the cart applies it (consumed only once the cart has items) and `llevarCarrito` moves a cart already built at another branch of the same company. The chosen branch's `createOnlineOrder` revalidates everything as always. The menu header offers "Cambiar sucursal" and the cart's "No llegamos" links back when the company has more than one (`OnlineMenu.sucursalesOnline`). `companies.online_alias` is the company's short link (`saveCompanyOnlineAlias`, shown in Pedido online for every company as the cover's link); it shares the namespace with branch aliases and `resolveOnlineAlias` checks it first, returning `local: null`. `bun run src/db/migrate-alias-empresa.ts` adds the column. The company page also has a third option, **Menú · Solo mirar** (for a QR stuck in the shop): it picks a branch and opens its menu with `?ver=1` (`validateSearch` + the `SoloVer` context in `p.$empresa.$local.index.tsx`), which hides add buttons, bread picker, "repeat" and the cart bar, and offers "Pedir online" back to the company page. Each branch in Pedido online also shows a second QR, "QR para mirar el menú", pointing at that `?ver=1` link, so a single-branch company gets one too. The company page is the brand's cover (animated accent lights over a fading grid, a rotating ring around the logo, a live open/closed pill, a ticker and three steps; classes `portada-*` in `styles.css`, still under `prefers-reduced-motion`), and the logo in `OnlineHeader` links back to it.
- **Short link:** `online_settings.alias` (unique platform-wide, chosen by the owner in "Pedido online") makes `/{alias}` redirect to `/p/{empresa}/{sucursal}` (`src/routes/$alias.tsx`, `resolveOnlineAlias`). Static routes win over it, and every top-level route name must be in `RESERVED_SLUGS` (`src/lib/slug.ts`) so no alias can shadow it — add yours there when you create a new top-level route. `bun run src/db/migrate-link-corto.ts` adds the column. A custom domain per business (e.g. `primorosas.online`) is deliberately not wired to Railway: Hobby allows 2 custom domains per service; a registrar-side redirect to the short link costs no slot.
- **An online Mercado Pago order reaches the kitchen only once paid** (or switched to cash): `listKitchenOrders` filters out online MP orders still `pendiente` and not accepted, and `acceptOnlineOrder` refuses them. Since the order already deducted stock, an unpaid one expires after 30 minutes (`VENCE_PAGO_ONLINE_MS`): the kitchen refresh cancels it (only when Mercado Pago confirms there is no payment) and returns its stock, and its Mercado Pago link is created with the same expiry. A payment that still lands on a cancelled order is stored as `reembolso_pendiente` by `acreditarPedido`. Totem MP orders are unchanged: the customer is standing at the tablet.
- **The customer can cancel or switch payment method only until the business accepts the order** (`cancelOnlineOrder`, `changeOnlineOrderPayment`, public, by tracking token). After acceptance it is being prepared or on its way, and changes go by phone. Both updates are conditional on `accepted_at IS NULL AND status <> 'cancelado'`, and `acceptOnlineOrder` is conditional on not cancelled, so a simultaneous cancel and accept resolve to whoever lands first. Before cancelling or switching away from Mercado Pago the server asks Mercado Pago whether a payment just came in, so a paid order is marked `reembolso_pendiente` rather than lost. A customer cancellation leaves `cancelled_by` null — that is how the kitchen labels it "Lo canceló el cliente" and toasts it.
- The tracking page is addressed by a random `tracking_token`, never the sequential id, which would expose other customers' names, phones and addresses. `bun run src/db/migrate-pedido-online.ts` and then `migrate-envio-por-distancia.ts` create all of it.
- The online menu has a **search box** (name, description and combo contents, ignoring accents and case; while searching the menu is replaced by the matches) and **"repeat my last order"**: on a successful order the cart lines are saved on the phone per branch (`src/lib/online-repetir.ts`, 120 days), and the menu offers them when the cart is empty. Repeating rebuilds each line against today's menu — current price, name and gift rule, skipping what's gone and keeping only still-offered removals/extras — and opens the cart for review; the server validates as for any order. There is no customer account, so the phone is what remembers.
- **Opening hours** (`online_settings.horarios`, edited in Pedido online → Horario): shifts per weekday, several per day, a shift ending before it starts runs past midnight. `src/lib/horario.ts` computes open/closed and "abre hoy a las 19:00" in Argentina time (Railway runs in UTC), covered by `horario.test.ts`. Null or no shifts = always open while the channel switch is on. Outside hours the menu still loads (closed banner, live status pill) and the cart can be built, but sending is disabled and `createOnlineOrder` rejects it; `useHorario` re-evaluates every 30s so an open page notices. The manual switch still closes the channel at any time. `bun run src/db/migrate-horario-online.ts` adds the column.
- Online orders are **not printed yet**: printing happens on the totem tablet at the end of its flow, and an online order never passes through one.

### Totem cover and behaviour

`totemSettings` holds one row per company (template, colour base, hero image, eyebrow, title + accent, subtitle, CTA label, two badges, accent colour) and is edited in the admin's "Portada" section, which renders the real `TotemHome` inside `PreviewFrame` — an iframe with its own 1280x800 window, because the cover's `min-h-dvh` and `lg:` classes measure the window and a scaled div showed the phone layout. Fonts are pairs in `FUENTES` (`useTotemTheme.ts`); "geometrica" (Montserrat, weight 900 via `--totem-display-peso`) was added for Chiqui, and adding one means widening `totem_settings.font_theme` (`migrate-fuente-geometrica.ts`) and the Google Fonts link in `__root.tsx`. Three templates live in `src/components/totem/TotemHome.tsx`: `clasico`, `completo`, `split`. `useTotemTheme` tints every totem screen with the company's colour over the chosen base.

The customer's path is always visible: `TotemPasos` in the top bar shows which of the three steps they are on (elegí → tu pedido → confirmá), and `TotemCartBar` is pinned to the bottom of the browsing screens with the running total, appearing with the first product. Both answer the two questions somebody standing at a totem actually has — how much am I spending, and how do I go on — without them having to tap anything to find out. The cart and checkout pin their total and their button the same way, because the last thing you have to do on a screen should never be below the fold.

**Whoever adds a section to the panel must extend `user_permissions.section` in the database too.** That enum used to be rewritten wholesale by each migration with whatever list it knew about, and with two people working in parallel one of them silently dropped the other's section — it compiles, it boots, and it only fails when somebody tries to grant that permission. `bun run src/db/migrate-panel-sections.ts` rebuilds the enum from `PANEL_SECTIONS`, so the code is the source of truth; run it after adding one.

`useTotemIdleReset` sends the totem back to the cover and clears the cart after 90s without interaction, so one customer never inherits another's order. The cart (`src/lib/totem-cart.ts`) stores the slug it belongs to, empties itself if the tablet switches businesses, and keys each line by `kind + refId` so a product and a combo with the same id never collide.

### Images are stored in MySQL, not in object storage

There is deliberately **no S3/R2 integration**: the user rejected any vendor requiring a credit card. `ImageUploadField` resizes and re-encodes the file to WebP in the browser (max 1600px, quality 0.82 — a 550KB photo lands around 8KB), sends base64 to `uploadImage`, and the row goes into the `images` table. Files are served by `serveImage` in `src/lib/images.ts`, which `src/server.ts` intercepts at `/img/:id` **before the request reaches the router** — this is not a TanStack route. Ids are never reused, so responses are cached immutably. Old images are not garbage-collected when a cover is replaced.

### Server functions (`src/lib/api/*.functions.ts`)

All backend logic goes through TanStack Start server functions, not a separate API layer:

```ts
export const someFn = createServerFn({ method: "GET" | "POST" })
  .middleware([requireAuth])          // or requireSuperadmin, or omit for public
  .inputValidator(z.object({ ... }))  // zod schema, only for POST/mutations
  .handler(async ({ context, data }) => { ... });
```

- `src/lib/auth/middleware.ts`: `requireAuth` attaches `context.user: SessionUser` or throws; `requireSuperadmin` builds on `requireAuth` and additionally checks `user.roles.includes("superadmin")`.
- Handlers throw plain `Error`s with user-facing Spanish messages (e.g. `"Usuario o contraseña incorrectos"`) — these propagate to the client as the server-fn error and are shown via `sonner` toasts / inline alerts. Follow this convention rather than introducing structured error codes. What a handler throws arrives readable; what the `inputValidator` rejects arrives as zod's serialized issue array, so show it through `mensajeDeError` (`src/lib/error-message.ts`) instead of printing `err.message`, which would put raw JSON on screen.
- Route-level auth is enforced **client-side**, not via router `beforeLoad`: pages call `me()` in a `useEffect` and `navigate()` away if the user/role doesn't match (see `routes/login.tsx`'s `destinationFor`, `routes/admin.tsx`). The server functions are still the real security boundary via `requireAuth`/`requireSuperadmin`.

### Auth & sessions

Custom cookie-session auth (migrated off Supabase auth) in `src/lib/auth/`:

- `session.ts`: opaque random token stored in the `sessions` MySQL table, set as an httpOnly cookie; `getSessionUser()` joins `sessions` → `users` → `user_roles`. A session also dies after 12h without use (`last_seen_at`, refreshed at most every 5 minutes) — the only thing limiting a tablet left logged in at the counter.
- `throttle.ts`: five failed logins lock that identifier for 15 minutes (`login_attempts`). It counts by username/email rather than IP, which Railway's proxy makes unreliable; the trade-off is that someone can lock a known user out for a short while on purpose.
- The superadmin password is changed with `SEED_PASSWORD="..." bun run src/db/set-superadmin-password.ts`, which also drops that user's sessions.
- `password.ts`: password hashing (bcryptjs).
- `password-policy.ts`: the single rule for credentials — 8+ characters with a letter and a digit, no catalogue passwords, and an email that can actually receive mail. Every path that creates or changes a user must use `passwordSchema`/`emailSchema`; the user asked for this explicitly and it is covered by tests.
- **There is no password recovery by email yet.** The user chose to keep resets manual rather than add a mail provider: an owner resets his operators from Operadores, and the superadmin resets an owner from Credenciales. The email is validated because that flow is meant to arrive later; the login page says who to ask meanwhile. What does exist is `/cuenta` (`changeMyPassword`), where anyone logged in changes their own password — it asks for the current one even with a session open, so a tablet left unlocked can't lock its owner out.
- **Changing or revoking access must kill the open sessions.** `destroyUserSessions(userId, keepToken?)` in `session.ts` is called when an operator's password is reset, when a user is deactivated, when the superadmin changes an owner's credentials and when a company is deactivated (the session only checks whether the *user* is active, not the company). Without it, resetting the password of someone who just left changes nothing until their session expires on its own. Changing your own password keeps the current session and drops the rest.
- Roles are a many-to-many table (`user_roles`: `superadmin` | `admin` | `kitchen`) — a user can hold multiple roles; check with `roles.includes(...)`, not equality.

### Multi-tenant data model (`src/db/schema.ts`)

`companies` (tenant) → `locations` (branches) → `users` (superadmin has null `companyId`/`locationId`; `owner`/`encargado`/`kitchen` users are scoped to a company). **Every catalog table carries a non-null `companyId`** — `categories`, `products`, `combos`, `stockLimits`, and also `ingredients`, `ingredientCategories` and `actionCodes`, which used to allow `companyId: null` to mean "global, managed by the superadmin". That global concept was removed: what a business puts in its products is that business's data, so there is no shared catalog and the superadmin panel only administers companies. `action_codes.code` is unique per company, not platform-wide.

**Vocabulary:** an **empresa** is the tenant (`companies`) — what the superadmin creates and hands to an owner; a **negocio** is one of its branches (`locations`), created by the owner, e.g. "PrimoRosas Cariló". The UI used to call the tenant "negocio" and the branch "local"; that wording was corrected, while the table names stayed. Say empresa for the tenant and negocio for the branch in any user-facing copy.

Roles are `superadmin | owner | encargado | kitchen`. The superadmin has access to everything: `enterBusiness`/`exitBusiness` (`platform.functions.ts`) store the company being visited in an `acting_company` httpOnly cookie, and `getSessionUser` resolves `companyId` from it, so every company-scoped server function works unchanged while the superadmin is inside a business. An `encargado` is assigned one or more locations through `user_locations`; `src/lib/auth/scope.ts` (`accessibleLocationIds`, `assertLocationAccess`) is the single place that decides which locations a caller may touch, and `requireOwner` in `src/lib/auth/middleware.ts` guards owner-only operations (operators, locations).

Every server function that writes must check the permission, not just the company: `requireCompany` answers "do you belong here?", never "were you allowed to do this?". Two of them were missing it — `createMovement` let a read-only encargado move stock and cash, and `setOrderStatus` let any operator advance orders — so when adding a mutation, gate it with `requireEdit(section)` or an explicit `canEdit` check. The kitchen is the one place the permission matrix isn't enough: the `kitchen` role works there and has no sections ticked, so `assertCanViewKitchen`/`assertCanOperateKitchen` in `scope.ts` own that rule.

On the client, `ReadOnlyContext` (`src/components/admin/readonly.ts`) tells a section it is being viewed with "solo ver": sections hide the create button, the actions column and the status switches, and keep search, filters, sorting and paging. It is cosmetic — the server is still the boundary — but without it the panel offers buttons that always fail. `admin.tsx` computes the value and provides it; Comandera is not a panel section but its own screen, so it gets a plain link in the sidebar instead of a nav entry.

Per-location overrides (`locationProducts`, `locationCategories`) flip availability off for a specific branch; absence of a row means "available" (inherits from `product.active`/`category.active`).

`orders`/`order_items` are written by the totem checkout and read by `kitchen.tsx` through `src/lib/api/orders.functions.ts` (scoped to the caller's company via its locations). `order_items` snapshots product name and unit price, so editing a product later never rewrites past orders.

An order also carries the money side: `businessDate` (the jornada it belongs to), `paymentMethod` (`efectivo` | `mercadopago`) and `paymentStatus` (`pendiente` | `pagado` | `reembolso_pendiente`). `orderNumber` restarts at 1 every morning per location (assigned by the `order_sequences` counter above) — that is why the unique key is `(location, businessDate, orderNumber)` and why `businessDate` is stored instead of derived from `createdAt`. Cancelling is its own server function (`cancelOrder`), not a status change: it decides what happens to money already taken, and a cancelled order never goes back so the day's cash close doesn't change after the fact. `getCashClose` sums only what someone marked as cobrado, which is what you compare against the physical till; it takes a `desde`/`hasta` range of jornadas (the Recaudación section filters with `DateRangeFilter`, not a native `<input type="date">`, which in Chrome only opened its calendar when you hit the tiny icon).

A Mercado Pago payment is never marked by hand. `listKitchenOrders` asks Mercado Pago about MP orders still pending from the last 3 hours (at most 8 per refresh) and credits the approved ones, so an order whose customer walked away from the QR while the webhook got lost still ends up cobrado. In the kitchen, marking an MP order as cobrado first asks Mercado Pago (`verifyOrderPayment`); if Mercado Pago has no payment, `setOrderPaid` switches the order to `efectivo`, because the customer paid at the counter and the cash close has to match the till and the MP account separately. An order whose payment Mercado Pago confirmed (`mpPaymentId` set) cannot be unmarked — refunding it means cancelling. `verificarPagoMP`/`tokenDeEmpresa` live in `src/lib/payments/verificar.ts`, outside the `*.functions.ts` files, for the bundle reason below.

### Audit log

`audit_log` records the critical changes made from the panel — operators' permissions, sucursales and passwords, base and per-sucursal prices (bulk adjustments as one entry), Mercado Pago settings, unmarking a cobro, an MP order charged as cash, cancellations, sucursales and tótems created or removed, and the superadmin's changes to an owner's credentials, the slug and the company's status. Each row stores the user's email as well as the id (an operator can be deleted), whether it was the superadmin acting inside the company, a category, an already-written Spanish `summary` and optional before/after `details`. The Auditoría section (`AuditoriaSection`, owner-only, not delegable) lists it with date range, category and text filters; nothing edits or deletes rows.

Write entries with `registrarAuditoria(user, {...})` from `src/lib/audit/registrar.ts` **after** the change is made. It never throws — the change already happened — and logs to the server console instead. Never put secrets in it (the MP token is logged only as "cargó una credencial nueva"). When you add a mutation that touches permissions, money or access, add its audit entry in the same change. The table is created by `bun run src/db/migrate-audit-log.ts`.

**Selling deducts stock.** It did not until now: the `VENTA` action code existed marked `auto` and unused, and `vp_local` was always zero. `src/lib/stock/venta.ts` owns this — a plain module, not a `*.functions.ts` export, for the usual bundle reason. The deduction happens **when the order is taken**, so the inventory shows what is committed the moment it is committed; cancelling therefore has to give it back, and `devolverVenta` does, by reversing that order's own movements (`movements.orderId`) rather than recomputing recipes that may have changed since — it is idempotent, so a second cancel never returns twice. A resale product (`stockable`) deducts itself, an elaborated one deducts its recipe minus what the customer removed, and a combo deducts what its component products consume. A recipe line with no quantity deducts nothing: inventing a number there would quietly corrupt the count. The consumption is computed **before** the order transaction opens, and a failure there is logged and skipped — losing a sale because the stock could not be worked out is the worse of the two errors, the same rule Mercado Pago already follows. `bun run src/db/migrate-personalizacion.ts` creates all of it.

**Sold-out items stop selling** (`src/lib/stock/control.ts`): `productosAgotados` hides from both menus a resale product with no stock or an elaborated one whose recipe can't be covered (and the combos containing it), and `tomarPedido` re-checks with `faltantesDeStock` inside the order transaction, locking the `artistock` rows `FOR UPDATE` so two orders can't take the last unit. **Only stock somebody loaded is enforced**: an item is controlled from its first ingreso at that location (`artistock.control_desde`, set by `createMovement`); without that rule a company that never counted its inventory — most of them at the start — would sell nothing, because sales already left it negative. That first ingreso is the opening count, so it resets `vp_local`/`ep_local`, and `devolverVenta` doesn't give back sales older than `control_desde`. `bun run src/db/migrate-control-stock.ts` adds the column.

`movements` is an append-only ledger (`type`: `stock` | `caja`, `actionCode` from `action_codes`, signed `amount`) that is the source of truth for both stock and cash; `artistock.stockActual` is a MySQL _generated_ column (`ip_local - vp_local - ep_local`) derived from aggregated movement totals — don't write to `stockActual` directly, write a `movements` row and let the aggregates (`ipLocal`/`vpLocal`/`epLocal`) follow.

### Routing (TanStack Start file-based)

See `src/routes/README.md` for the file-naming convention (`$id` dynamic, `{-$cat}` optional, `$` splat, `_layout`, `__root.tsx`). `src/routeTree.gen.ts` is auto-generated — never hand-edit it. The only app shell/layout is `__root.tsx`; do not create Next/Remix-style `src/pages/` or `app/` directories.

### SSR error handling

There's a deliberate two-layer error wrapper because h3 (TanStack Start's server) can swallow in-handler throws into an opaque `{"unhandled":true,"message":"HTTPError"}` 500 that a plain `try/catch` won't see:

- `src/start.ts` registers `errorMiddleware` (catches request-level errors, renders `renderErrorPage()`).
- `src/server.ts` wraps the whole `fetch` handler and additionally detects/normalizes the swallowed-h3-error JSON shape via `src/lib/error-capture.ts` + `src/lib/error-page.ts`.

Don't remove either layer when touching server entry code — they cover different failure modes.

### Vite config

`vite.config.ts` uses `@lovable.dev/vite-tanstack-config`'s `defineConfig`, which already wires up `tanstackStart`, `viteReact`, `tailwindcss`, `tsConfigPaths`, nitro, the `@` path alias, and dev-only plugins. Do not add these plugins manually — the comment in the file warns this causes duplicate-plugin breakage. Pass extra config via the `vite`/`tanstackStart` keys of `defineConfig` instead.

### UI conventions

- **Vocabulary: a location is a "Sucursal" in the UI.** The tenant is an *empresa* (`companies`); each branch (`locations`) is shown as **Sucursal / Sucursales** in all user-facing text (Nicolas' decision, replacing the earlier "Negocio"). Keep gender agreement — *sucursal* is feminine (una sucursal, la sucursal, las sucursales). The delivery method label "Comer en el local" is unrelated (dine-in) and stays. Internal identifiers stay in English (`locations`, `locationId`, `LocalesSection`).
- **Scrollbars use the system colour.** All scrollbars in the app are styled globally in `src/styles.css` with the `*` selector: `scrollbar-color: var(--primary) transparent` plus the `::-webkit-scrollbar` rules (thin, rounded thumb in `var(--primary)`, transparent track). Do not add per-element scrollbar styles that diverge from this; if a new surface scrolls, it inherits the global style automatically. In the totem `var(--primary)` follows the chosen theme, so the bars re-colour per shop.

### Deployment

Built with the Dockerfile (bun for install/build → `node:22-slim` runtime running the nitro `node-server` preset output, `.output/server/index.mjs`) and deployed to **Railway** per `railway.json`. `DATABASE_URL` (Railway MySQL) is read from `.env.local` locally and from Railway env vars in production.

## Known gaps (next steps)

Verified working end to end: business signup → owner login → cover setup → image upload → catalog on the totem → cart → checkout → order in the DB → kitchen panel. What is still missing:

- The slug **is** editable, but only by the superadmin (`updateBusinessSlug`), because changing it breaks the previous link and any printed QR. The full totem URL and its QR show in the Portada section (`TotemLinkCard`). A company left without an owner is no longer a dead end either: `assignBusinessOwner` creates one.
- **Mercado Pago charges per company, into the company's own account.** Each owner pastes their access token in the Cobros section; it lives in `payment_settings`, never leaves the server, and `getTotemMenu` only exposes a boolean so the totem knows whether to offer the button. Paying is a QR on the totem screen that the customer scans with their phone (`/t/$empresa/$local/$totem/pagar/$orderId`), built from a Checkout Pro preference. The order is saved **before** asking Mercado Pago for the preference, so if Mercado Pago is down the order is still taken and the counter can charge cash.

  Two things confirm a payment: the webhook at `/api/mp/webhook` (intercepted in `src/server.ts`, like `/img/`), and the totem asking every few seconds while the customer pays. The poll is not a development crutch — the webhook can be lost in production too, and there is someone standing in front of the screen. The webhook takes **only the payment id** from the notification and asks Mercado Pago for the rest, because that endpoint is public and anyone can hit it claiming an order was paid.

  **Never export a plain function that touches the database from a `*.functions.ts` file.** Only server functions get stripped from the client bundle; an ordinary export stays and drags drizzle and the MySQL driver into the browser, which throws on load and leaves the whole app without JavaScript. That is why `acreditarPedido` lives in `src/lib/payments/acreditar.ts` and not next to the totem's server functions.
- **Prices are per company, not per location** (point 6 of the business rules), and neither is the price-change audit. Same for a location's own products and for per-product customisation (points 5 and 7).
- A logged-in session on the totem tablet used to be a hole — the totem screen has no way out, but the address bar does. The link the panel hands out for the tablet now ends in `?totem=1`: `useTotemDevice` marks that browser and, every time the cover loads, calls `leaveStaffSession` to drop any panel session left open there. `?totem=0` removes the mark, and the panel's own "Abrir" button uses the bare link so previewing from a PC doesn't log you out. It is still worth locking the tablet in the OS kiosk mode.
- **`.env` is committed to the repo**, so its keys are in git history. Pre-existing, flagged to the user, untouched — removing it means rewriting history and rotating keys.
